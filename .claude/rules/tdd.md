# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 프로젝트별 규칙이 없을 때 적용하는 **기본값(fallback)** 이다.

## 1. 적용 기준

### 반드시 TDD 적용

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리, 에러 매핑)
- **유틸 함수** (순수 함수, 변환/파싱/검증)
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의 (`interface`, `type`)
- 설정 파일 (`vite.config.ts`, `tsconfig.json`, `eslint.config.js` 등)
- 순수 UI (로직 없는 마크업, 스타일링)
- SQL (스키마, 마이그레이션)

경계가 모호하면 **적용하는 쪽**으로 판단한다.

## 2. RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 RED가 아니므로 테스트를 고쳐 다시 실행한다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능, 분기, 옵션을 넣지 않는다.
- **신규 테스트와 기존 테스트가 모두 통과**하는지 실행해서 확인한다.

### REFACTOR: green 상태에서 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- 모든 테스트가 **green을 유지**해야 한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 요구사항이 모두 테스트로 표현될 때까지 반복한다.

## 3. 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제**하고 RED부터 재시작한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 임시 파일, 별도 브랜치 보관 모두 포함한다. 보고 베끼는 순간 테스트 우선이 아니다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드일수록 테스트 작성이 몇 초면 끝난다. 단순한 코드가 깨지는 버그가 가장 늦게 발견된다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰 작성되어 결함을 잡지 못한다. 그 "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드의 디버깅과 회귀 수정이 더 오래 걸린다. 시간이 없을수록 RED-GREEN을 지킨다. |
| 삭제하면 낭비다 | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| 프로토타입이다 | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라고 확정되지 않았다면 TDD를 적용한다. |
