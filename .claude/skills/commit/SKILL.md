# commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋을 만든다. **사용자 승인을 받지 않고 바로 커밋한다.** 이 스킬이 호출되었다는 것 자체가 커밋 허락이다.

## 절차

### 1. 변경사항 분석
다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # unstaged
git diff --staged   # staged
git log --oneline -10   # 기존 메시지 스타일 참고 (커밋이 없으면 생략)
```

- untracked 파일은 `git status`로 확인하고 필요하면 내용을 읽는다.
- `.env`, 키, 토큰 등 비밀 정보나 `node_modules`, 빌드 산출물은 커밋 대상에서 제외하고 결과 보고 시 알린다.

### 2. 논리적 단위로 분류
- 하나의 커밋은 **하나의 목적**만 담는다 (기능 추가, 버그 수정, 리팩터링, 설정 변경을 섞지 않는다).
- 파일 단위로 나눈다. (`git add -p`는 비대화형 환경에서 불가하므로 한 파일에 목적이 섞여 있으면 해당 파일은 하나의 커밋으로 묶는다.)
- 커밋 순서는 의존 관계를 고려한다 (설정/의존성 → 핵심 로직 → UI → 문서).

### 3. 커밋 메시지 작성
형식:

```
<type>: <한국어 요약>

(선택) 본문: 무엇을/왜 바꿨는지
```

| type | 용도 |
|------|------|
| feat | 새로운 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 빌드, 설정, 의존성, 기타 잡무 |

규칙:
- 요약은 50자 안팎, 마침표 없이, 명사형 또는 `~추가`/`~수정` 형태로 끝낸다.
- "무엇"보다 "왜"가 중요하면 본문에 적는다.
- 위 4개 외 type(docs, style, test 등)은 사용자가 요청할 때만 쓴다.

### 4. 즉시 커밋
1. 커밋 단위별로 `git add <파일>` 후 `git commit`을 실행한다. `git add -A`/`git add .`는 쓰지 않는다. 승인을 묻지 않는다.
2. 완료 후 `git log --oneline -n <커밋 수>`로 결과를 요약해 보고한다 (커밋 해시, 메시지, 제외한 파일과 이유).

## 주의
- 사용자가 명시적으로 요청하지 않으면 `git push`, `--amend`, `--no-verify`, force 옵션을 쓰지 않는다.
- pre-commit hook이 실패하면 원인을 고치고 **새 커밋**으로 다시 시도한다.
- 변경사항이 없으면 커밋하지 않고 그 사실만 알린다.
- 커밋 메시지 끝에 시스템이 지정한 Co-Authored-By 등 attribution 줄이 있으면 그대로 덧붙인다.
